## 0. 本版变更（v3 → v4）

| # | 变更项 | v3 | v4 |
|---|---|---|---|
| 1 | 区分说话人 | 必做，双 ASR 通道（MIMO / paraformer-v2） | **占位入口，禁用 + 弹窗，不做后端** |
| 2 | ASR 通道 | 两条 | **一条（MIMO）**，百炼仅用于实时录音 |
| 3 | 离线识别链路 | 临时上传凭证 → OSS → 异步任务 → 轮询 | **整条移除**（代码不写、配置不加） |
| 4 | 数据模型 | `jobs` + `speakers` + `segments` | `jobs` + `segments`（`speaker_fk` 字段预留恒 NULL，`speakers` 表不建） |
| 5 | 详情页 | 说话人分组 / 重命名 / 6 色板 | 单一文本流，按时间戳分段 |
| 6 | 进度阶段 | 含 `UPLOADING_REMOTE` / `DIARIZING` | 移除两项，权重重新分配 |
| 7 | WBS | 12 项（含 B3/B6） | **10 项**，删除 B3（离线识别）、B6（录音收尾替换） |
| 8 | 关键路径 | `D0 → B1 → B3 → B4 → F4 → Q1` | **`D0 → B1 → B2 → B3 → F4 → Q1`**（少一环，且不再有最高风险项） |

**收益**：开发量明显下降，最高风险项（临时上传 + 异步轮询 + 2h 上限）从本期消失；1.5h 录屏端到端目标从 ≤12 分钟收紧到 **≤8 分钟**（不再有分离耗时）。

**代价**：纪要里无法标注「谁说的」。补偿手段只有时间戳回跳 + 用户在纪要文本里自行补充，这个限制必须在 UI 上说清，不能沉默。

## 2. 范围界定

### 2.1 本期做

- 首页三入口：**上传视频 / 上传音频 / 实时录音**
- 上传视频：本地解析（ffprobe）→ 抽音频 → 30s 静音对齐切片 → MIMO 并发转写 → 可选生成纪要
- 上传音频：同上，跳过视频轨处理
- 实时录音：浏览器采集 → 服务端 WebSocket 代理百炼 → 实时字幕 → 结束生成纪要；支持暂停/续录
- 纪要：map-reduce（分片摘要 → 合并）+ 结构化 JSON
- 详情页：转写全文（时间戳可回跳）+ 纪要区 + 导出 md
- **「区分说话人」占位入口**：禁用态卡片 + 弹窗（见 §6）

### 2.2 本期明确不做（附理由，避免后续反复）

| 不做的事 | 理由 |
|---|---|
| 说话人分离（任何实现方式） | 已决定延后；qwen filetrans 的 `speaker_id` 实测恒 0，paraformer 可用但需引入 OSS 上传链路 |
| 离线识别 / 临时上传凭证 | 唯一用途是分离，随上一条移除 |
| 本地 sherpa-onnx 模型 | 44MB 模型 + 1 小时约 8 分钟耗时，本期无收益 |
| 参会人数选择控件 | 没有分离就没有聚类，控件无意义 |
| `speakers` 表 | 无数据写入；开功能时再加迁移 |
| 分片上传 / 断点续传 / 鉴权 | 本机单用户，收益为零 |

## 3. 架构（单通道）

### 3.1 上传视频 / 音频

```
文件 → ffprobe（时长/音轨/编码）→ 抽 16k 单声道 wav（highpass + loudnorm）
  → silencedetect 找静音 → 30s 为一个转写单元（静音点对齐）
  → MIMO 并发 4 逐片转写 → 字率护栏（<1.5 字/秒 → 该片转百炼兜底）
  → segments（start_ms/end_ms/text，speaker_fk = NULL）
  → 输出=纪要 ? map-reduce 生成 → 详情页
```

- 时间戳精度：**片级**（≈30s 一跳）
- 引擎：`mimo-v2.5-asr`（沿用现有 key）
- 不外传、不计费、无上传额度限制

### 3.2 实时录音

```
AudioWorklet 48k → 降采样 16k Int16 → 100ms/帧 → /ws/record → 百炼流式
  → result-generated（sentence_end=true 终稿）→ 按 sentence_id 覆盖渲染
  → 结束 finish-task → 流式终稿直接落 segments（已含句级时间戳）
  → 生成纪要 → 详情页
```

> 录音链路**结束时不调用 MIMO**：流式终稿已有句级时间戳，重跑一遍等于同一段音频处理两次。这是决策 4「静态音频用 MIMO」的唯一例外，理由是避免无意义重复。

### 3.3 两条链路对照

| 链路 | 引擎 | 切片 | 时间戳 | 说话人 |
|---|---|---|---|---|
| 上传视频/音频 | MIMO | 30s 静音对齐 | 片级 | 无（字段预留） |
| 实时录音 | 百炼流式 | 服务端 VAD 断句 | 句级 | 无（字段预留） |

## 4. 长音频处理

### 4.1 30 秒切片

- `silencedetect=noise=-35dB:d=0.6` 拿静音区间，以 30s 为目标，在 `[19.5s, 40.5s]` 窗口内选**离目标最近的静音中点**下刀
- 找不到静音点才硬切，**不留重叠**（重叠会让同一句被识别两次）
- 每片校验：时长 >2s、RMS > -50dB；纯静音片直接丢弃（共享屏幕时常见，省时间）
- 并发 4；1 小时约 40 片，实际 2~3 分钟；1.5 小时约 60 片，约 4~5 分钟

**为什么是 30s（实现时由 90s 改来）**：实测同一段真实语音，30s 切 6 片全部正常（144~160 字/片，字率 4.8~5.3），45s 有 1 片只出 126 字（中途截断），92s 只剩 8 字与 5 字。MIMO 的截断与时长正相关且极陡，30s 是唯一稳定区间。代价是片数×3，但单片只要 1.4s，1 小时约 120 片、并发 4 仍在一分钟内（实测见 §16）。

### 4.2 边界保护

- **字率护栏**：单片输出 < 1.5 字/秒 → 判为退化，该片改走百炼流式重转（同一适配层，已有实现）
- 拼接用「前片尾部 40 字 + 后片头部 40 字」做最长公共子串去重（仅硬切时可能触发）
- 片数与时间轴落库，中途 kill 后可只补未完成片

### 4.3 音频规格

| 项 | 值 | 原因 |
|---|---|---|
| 采样率 | 16kHz | MIMO 与百炼的最优输入 |
| 声道 | 单声道 | 双声道混合会串音；本期无拆声道需求 |
| 编码 | mp3 64kbps | 省带宽，MIMO 实测可接受 |
| 处理链 | `highpass=f=80` + `loudnorm` | 会议录音常见低频嗡声与音量不齐 |

## 6. 「区分说话人」占位入口规格

这是本版唯一的**新增交互**，也是最容易做错的地方：做得好用户知道「以后会有」，做得差用户以为「坏了」。

### 6.1 视觉

```
┌────────────────────────────────────────────────┐
│  区分说话人          [开发中]        [ ●─── ]  │
│  自动标出每句话由谁说出，后续版本开放            │
└────────────────────────────────────────────────┘
```

- 位置**固定**在输出类型分段控件下方（不因禁用而移除或下移）——位置留白比整块消失更容易让用户理解「功能存在但未开放」
- 卡片高度 76px，背景 `--paper-2`，边框 1px `--line-1`，**不加 accent 描边**（无激活态）
- 标题 `--ink-2`（非纯黑），副文案 `--ink-3`
- 右上角徽标「开发中」：`--warn-bg` 底 + `--warn-text` 字，11px，圆角 4，padding 2px 6px
- 开关用**纯视觉元素**渲染为关闭态，整体 `opacity: .55`，**不出现动画、不出现 hover 高亮**
- 鼠标 `cursor: not-allowed`
- **不显示**「参会人数」「开启后按分钟计费」——开关永远无法打开，摆出这些只会误导

### 6.2 交互与实现口径

关键点：**`disabled` 的 `<input>` 不派发 click 事件**。如果直接把开关设成 `disabled`，父级监听也收不到点击（部分浏览器），弹窗永远弹不出来。因此：

- 开关**不用 `<input disabled>`**，改用 `<span class="switch is-off" aria-hidden="true">` 纯视觉
- 整张卡片承担点击：`role="button" tabindex="0"`，用 `aria-label="区分说话人，功能开发中，点击了解详情"` 说明状态
- 事件：`click` + `keydown`（`Enter` / `Space`）→ 打开弹窗
- **不要用 `aria-disabled="true"`**（实现时踩到）：它表示「这个控件不可操作」，而这张卡恰恰是可操作的——点击会打开说明。标了之后屏幕阅读器会说「不可用」，自动化工具（实测 Playwright）甚至判定元素不可点击而拒绝交互，与真实行为矛盾。正确做法是普通 button 语义 + `aria-label` 里写清「功能开发中」
- `tabindex="0"` 保留是**有意为之**：真正的 disabled 控件不可聚焦，键盘用户就永远看不到解释文案

### 6.3 弹窗规格

- **不用 `alert()`**：阻塞主线程、样式不可控、无法做焦点管理、与纸感设计冲突
- 自建轻量 modal：遮罩 `rgba(28,26,23,.42)` + `backdrop-filter: blur(2px)`
- 面板：宽 420px，纸色 `#fffdf8`，圆角 14，padding 24，`box-shadow: 0 18px 48px rgba(0,0,0,.18)`
- 层级：遮罩 `z-index: 900`，面板 `901`（低于 toast 1000）
- 动画：`opacity 0→1` + `translateY(4px→0)`，120ms；`prefers-reduced-motion` 时直接显示
- 打开时焦点移到「知道了」；关闭后**焦点返回卡片**（否则键盘用户会掉到页面顶部）
- 关闭方式三种：主按钮 / `Esc` / 点遮罩
- 打开期间：`body` 加 `overflow:hidden`，遮罩内 `Tab` 循环（焦点陷阱，仅 1 个可聚焦元素时可简化）

**文案（定稿）**

| 项 | 内容 |
|---|---|
| 标题 | 区分说话人 |
| 正文 | 这个功能会自动标出每句话是谁说的，目前还在开发中，暂时不能开启。\n你可以先完成转写和纪要，点击时间戳可以回到对应位置。 |
| 按钮 | 知道了 |

> 正文必须给出「现在能做什么」，只写「开发中」会让用户卡在原地。

### 6.4 状态矩阵

| 触发 | 结果 |
|---|---|
| 鼠标悬停 | 卡片不变色，`cursor: not-allowed`，无 tooltip |
| 单击 | 弹窗打开，**开关视觉状态不变**（不出现开启动画） |
| `Tab` 聚焦 | 卡片有 2px `--accent` 焦点环 |
| `Enter` / `Space` | 弹窗打开 |
| `Esc` / 遮罩 / 知道了 | 弹窗关闭，焦点回卡片 |
| 页面刷新 | 仍为关闭态（无本地存储，不记忆） |
| 弹窗打开时再点卡片 | 无叠加，仅有 1 个实例（`document.querySelector` 去重） |

### 6.5 录音视图的差异

录音视图**不出现**该占位卡片。理由：录音流程是「点开始 → 说完 → 结束」，中间插入一个不可操作项会让用户以为必须先处理它才能录音；上传视图有充足空间说明「以后会有」，录音视图没有。

## 8. 两条主流程

### 8.1 上传视频 / 音频

```
选文件 → 预检（扩展名 / 大小 ≤2GB / 时长 ≤4h）
→ 上传到本地磁盘（0–6%）
→ ffprobe（6–7%）→ 抽 16k 单声道 wav（7–14%）
→ 30s 静音对齐规划切点（14–20%）
→ MIMO 并发 4 转写（20–85%）+ 字率护栏
→ 写 segments（speaker_fk = NULL）
→ 输出=纪要 ? map-reduce（85–100%）: 跳过
→ 详情页
```

异常分支：

- 无音轨 → ≤3 秒报错「该文件没有音频轨，无法转写」
- 文件损坏 / ffprobe 失败 → 提示具体原因，不吞错误
- 全片字率 < 1.5 字/秒 → 整体转百炼兜底，并在结果页标注「已使用备用引擎」
- 进程中断 → 重启后只补未完成片

### 8.2 实时录音

```
开始录音 → 请求麦克风 → 建立 /ws/record
→ AudioWorklet 48k → 16k Int16 → 100ms/帧 → 百炼流式
→ 句级回传 → 按 sentence_id 覆盖渲染
→ 结束 → finish-task → 流式终稿落 segments
→ 生成纪要 → 详情页
```

**暂停/续录（决策 5）**

- 时间轴 = 已推送音频时长，不是墙钟
- 暂停：停推 PCM（含静音帧）→ 音频时钟不前进 → 时间轴自然跳过
- 暂停瞬间补一帧静音，促使当前句 `sentence_end`，防止跨暂停两句粘连
- 继续：从当前音频时钟续推
- 验收：录 3min → 暂停 1min → 录 2min = 时间轴 5min

**轮转**：满 20 分钟自动 `finish-task` + 新 `run-task`，音频时钟累加，用户无感。

**断线**：3 次重连（每次新建 task），保留已确认句；仍失败则提示「转写已中断，已保存 X 分 Y 秒」。

## 9. 数据模型

```sql
CREATE TABLE jobs (
  id            TEXT PRIMARY KEY,
  source_type   TEXT NOT NULL,        -- video | audio | recording
  file_path     TEXT,
  audio_path    TEXT,
  duration_ms   INTEGER,
  effective_ms  INTEGER,              -- 录音=有效时长（跳过暂停）
  engine        TEXT,                 -- mimo | bailian_stream
  status        TEXT,                 -- queued|running|done|failed|canceled
  stage         TEXT,
  progress      REAL DEFAULT 0,
  error         TEXT,
  options_json  TEXT,                 -- 预留：将来存 {diarization:true, speaker_count:N}
  created_at    TEXT, updated_at TEXT
);

CREATE TABLE segments (
  id          TEXT PRIMARY KEY,
  job_id      TEXT NOT NULL,
  idx         INTEGER NOT NULL,
  start_ms    INTEGER NOT NULL,
  end_ms      INTEGER NOT NULL,
  speaker_fk  TEXT,                   -- 预留，本期恒 NULL
  text        TEXT,
  status      TEXT,                   -- pending|done|failed|fallback
  engine      TEXT,
  retry       INTEGER DEFAULT 0,
  UNIQUE(job_id, idx)
);

CREATE INDEX idx_segments_job ON segments(job_id, start_ms);
```

两个刻意的预留（成本近零，但能让后续开关避开破坏性迁移）：

1. `jobs.options_json` 留空对象，将来存分离参数，不用加列
2. `segments.speaker_fk` 恒 NULL，将来只加 `speakers` 表与外键，不改 `segments`

> `speakers` 表本期**不建**：没有写入方，建了就是死表，反而让人误以为功能已存在。

## 11. 开发顺序与依赖

```
D0 ─┬─ F1 ────────────────────────────────┐
    ├─ B1 ─┬─ B2 ─ B3 ─ F4 ───────────────┤
    │      └─ B4 ─ F3 ────────────────────┤
    └──────────── F2 ─────────────────────┘
                                          Q1
```

**关键路径**：`D0 → B1 → B2 → B3 → F4 → Q1`

排序理由：

1. **B1 先做**：`jobs`/`segments` 是上传与录音两条链路的公共地基，晚做会导致两边同时返工
2. **B2 紧随**：默认路径，且 `server/audio.js` 与 `asr-bailian.js` 已就绪，改造成本最低、见效最快
3. **B3 依赖 B2**：纪要吃的是 segments，segments 不稳定时调纪要等于在错的数据上调 prompt
4. **B4 可独立并行**：只依赖 B1，与 B2 互不干扰，适合两人同时开工
5. **F2 依赖 B1 但不依赖 B2/B3**：接口定型即可开工，是前端的提前量

## 附录 A · 已归档的技术验证（本期不实现，留档备查）

> 这部分是 v3 期间真实跑过的实测数据，价值在于：将来要开「区分说话人」时不必重跑，也避免再次误选引擎。

### A.1 四条链路的能力边界

| 引擎 | 时间戳 | 说话人 | 长音频 | 结论 |
|---|---|---|---|---|
| `mimo-v2.5-asr` | ❌ | ❌ | ❌ 45s 起截断、90s 只剩 8 字 | 只能做 30s 片段（配合 30s 切片 + 护栏） |
| 百炼流式 `...-streaming` | ✅ 句级 | ❌ 恒 null | ✅ 边推边出 | 实时字幕唯一选择 |
| `qwen-audio-3.x-asr-flash-filetrans` | ✅ 句级 | ⚠️ 名义支持，**实测恒 0** | ✅ ≤2h | 文本质量最好，但不能用于分离 |
| `paraformer-v2` | ✅ 句级（ms） | ✅ **实测正确** | ✅ | 若将来做分离，默认引擎选它 |

### A.2 说话人分离实测（同一套 `diarization_enabled: true`）

| 音频 | 引擎 | 句数 | `speaker_id` 分布 |
|---|---|---|---|
| 93s 双人对话（男女声，16 轮交替） | qwen 3.0 filetrans | 18 | `{0: 18}` ❌ |
| 374s 双人对话（同内容循环 4 次） | qwen 3.0 filetrans | 83 | `{0: 83}` ❌ |
| 93s 双人对话 | qwen **3.1** filetrans | 18 | `{0: 18}` ❌ |
| 36s 真人多人录音 | qwen 3.0 filetrans | 7 | `{0: 6, 1: 1}` ❌ |
| **93s 双人对话** | **paraformer-v2** | 19 | **`{0:10, 1:9}` ✅ 与真实轮次完全对应** |

**判定**：参数格式正确（paraformer 同参数即生效），是 qwen filetrans 在当前 workspace 下 `speaker_id` 为空实现。将来若直接开 qwen 分离，会得到「只有一个说话人」的假功能。

### A.3 MIMO 时长退化

7s 正常 / 60s 只出 10 字 / 120s 正常 / **300s 出 4 字 / 600s 出 5 字**；`usage.seconds` 与 `audio_tokens` 表明音频已送入，是输出侧退化，**调参数无效**，只能靠切片规避。

### A.4 本地分离（sherpa-onnx）

`sherpa-onnx-node` 在 macOS arm64 跑通，pyannote 分割（5.7MB）+ eres2net 声纹（38MB），RTF≈0.13，纯 Node 无需 Python。已知缺陷：输出重叠区间需消解、`numClusters=-1` 过度聚类（5 分钟判出 10 人）、1 小时约 8 分钟。是「完全离线 + 要分离」场景的唯一可行路线。

### A.5 本地文件喂离线识别

离线识别只收 HTTP/HTTPS/`oss://`。实测可用 DashScope 临时上传凭证打通，不需要对象存储与公网 IP：

```
GET  {ws}.cn-beijing.maas.aliyuncs.com/api/v1/uploads?action=getPolicy&model=<model>
POST {upload_host}  (multipart: OSSAccessKeyId / Signature / policy / key / file)
POST /api/v1/services/audio/asr/transcription   (X-DashScope-Async: enable) → task_id
GET  /api/v1/tasks/{task_id}  → SUCCEEDED → transcription_url → JSON
```

实测 600 秒音频提交到出结果 12 秒，`usage.duration=534`（按语音内容计费，静音不计）。

## 16. 实施记录（v4 落地后的实测与偏差）

> 本节记录「实际做出来的样子」，与前面章节冲突时以本节为准。

### 16.1 实测数据

| 场景 | 结果 |
|---|---|
| 36 秒真人录音（单段） | 转写 + 纪要全链路 12 秒内完成，纪要 JSON 结构正确 |
| 12 分钟音频（21 段） | 端到端 **24 秒**（约 30 倍实时），21 段全部由 MIMO 完成，**零兜底**，3634 字 |
| MIMO 30s × 6 片 | 6/6 正常，144~160 字/片，字率 4.8~5.3 |
| MIMO 45s × 4 片 | 4/4 有输出，但 1 片只出 126 字（中途截断） |
| MIMO 92s × 2 片 | **8 字 / 5 字**，几乎全丢 |
| 实时录音（虚拟麦克风 13 秒） | 首字 ≈1.5 秒；暂停 4 秒期间计时器冻结在 00:09；继续后 4 秒到 00:13（暂停段正确跳过） |
| 无音轨 mp4 | **0.1 秒**拒绝，返回「该文件没有音轨，无法转写」 |
| 中途取消 12 分钟任务 | 已完成的 8 段保留，状态 canceled |
| 对取消的任务续跑 | 从第 8 段补到 21 段，用时 12 秒，无重复段 |
| 进程重启 | 启动时把 running/queued 标为 failed 并提示可续跑 |

### 16.2 与计划的偏差（3 处，都已改进代码与本文）

1. **切片段长 90s → 30s**。计划的 90s 基于「300s 才崩」的旧数据；实测 45s 就开始截断。改为 30s 后兜底率从 2/8 降到 0/21。
2. **占位入口去掉 `aria-disabled`**。它会让辅助技术（以及 Playwright 的可操作性判定）认为元素不可交互，而这张卡点击要弹说明，语义自相矛盾。改为普通 button 语义 + `aria-label` 写明「功能开发中」。
3. **短会议跳过 map**。单块文本直接进 reduce，13 秒录音的纪要从 41 秒降到约 20 秒；map 并发 2 → 4。
